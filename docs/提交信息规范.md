# 提交信息规范

面向：所有向本仓库提交代码的人。
适用范围：本仓库全部分支。规范本身采用 [Conventional Commits](https://www.conventionalcommits.org/)。

---

## 0. 一句话规矩

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **subject 说「做了什么」，body 说「为什么」。** 只有 subject 的提交等于没写 body 的那一半信息。
- subject ≤ 72 字符，祈使句，句尾不加句号。
- type 必填，scope 可选但强烈建议填。

---

## 1. 为什么要立这个规矩

不是洁癖。近 60 条提交实测：

| 现象 | 条数 | 后果 |
| --- | --- | --- |
| subject 以 `Add ` 开头 | 21 / 60 | `git log --oneline` 满屏 `Add`，无法据此定位改动 |
| subject 超过 72 字符 | 15 / 60 | 长 subject 在 `git log`、GitHub 列表、`git bisect` 里被截断 |
| 完全没有 body | 17 / 60 | 「为什么这么改」只存在于当时那个人的脑子里 |
| `Merge branch 'dev' of https://...` 噪声提交 | 4 / 60 | `git pull` 不 rebase 产生的，污染历史且无信息量 |
| 带 type 前缀 | 6 / 60 | 无法自动生成 changelog，无法按类型过滤 |

具体的坏样本（都在本仓库历史里，可以直接 `git show` 看）：

```
3f1d0bcb34  Refactor XqGigaProductMapper and related services to enhance product
            pagination and caching. Introduced new methods for counting and
            retrieving product IDs, optimized SQL queries ...
            → subject 269 字符，整段正文塞进标题行，body 为空

d1ce1bce3c  Optimize XqProductServiceImpl for improved performance and caching
            - Introduced a short-term cache for unfiltered
            → 113 字符，用 " - " 把 body 接到 subject 后面，句子还是断的

f968d7a75f  Add new JSON files and a Python script for inventory statistics
            → 描述的是文件类型，不是意图。半年后没人知道这几个 JSON 是干什么的
```

三条的通病是同一个：**标题行承担了正文的职责，正文因此是空的**。

---

## 2. type：必填

| type | 用在 | 例子 |
| --- | --- | --- |
| `feat` | 新功能 | `feat(ai): 支持批量生成商品文案` |
| `fix` | 修 bug | `fix(work-order): 分表模板路径为空时抛 NPE` |
| `docs` | 只改文档 / 注释 | `docs: 补提交信息规范` |
| `refactor` | 改结构不改行为 | `refactor(product): 抽出分页查询的公共条件` |
| `perf` | 改行为提升性能 | `perf(product): 给未过滤查询加短期缓存` |
| `test` | 只加/改测试 | `test(tenant): 去掉 H2 无法回环的时间戳断言` |
| `build` | 构建系统、依赖 | `build(deps): bouncycastle 1.80 → 1.85` |
| `ci` | CI 配置 | `ci: Maven 改走 Central，冷构建 23min → 7m45s` |
| `chore` | 杂项，不改源码也不改测试 | `chore: gitignore 补本地配置路径` |
| `revert` | 回滚 | `revert: feat(ai): 批量生成文案` |
| `security` | 修安全问题 | `security(config): 短信验证码放开为随机区间` |

**判不准就用 `fix` 或 `feat`**，别为了选 type 卡住。但下面两条别混：

- 改了行为 → 不是 `refactor`
- 顺手清理的死代码 → 不要塞进 `feat`，单独一个 `chore`

`security` 是本仓库在上游 Conventional Commits 之外加的：涉及凭据、鉴权、越权、加密的改动
一律用它，方便 `git log --grep '^security'` 一次拉出全部安全相关变更。

---

## 3. scope：可选，但强烈建议

用模块名去掉 `yudao-module-` / `yudao-spring-boot-starter-` 前缀：

| scope | 对应 |
| --- | --- |
| `system` | `yudao-module-system` |
| `infra` | `yudao-module-infra` |
| `fms` | `yudao-module-fms` |
| `ai` | `yudao-module-ai` |
| `mybatis` / `redis` / `security` / `web` / `mq` / `excel` / `job` / `tenant` / `data-permission` | `yudao-framework` 下对应 starter |
| `server` | `yudao-server` |
| `deps` | `yudao-dependencies`（版本钉子都在这） |

跨模块或不属任何模块的，用领域词：`ci`、`docker`、`config`、`sql`、`docs`、`gitignore`。

改动横跨多个模块时 **不写 scope**，比乱挑一个更诚实：`feat: 工单关联商品分表`。

---

## 4. subject：≤72 字符，祈使句

- **祈使句**：`Add`、`Fix`、`Remove`，不是 `Added`、`Fixes`、`Adding`。
  判据：能不能接在 "This commit will ___" 后面。
- **句尾不加句号。**
- **首字母大写，type/scope 之后空一格。**
- **说意图，不说文件类型。** `Add inventory statistics seed data` 胜过
  `Add new JSON files and a Python script`。
- **一个提交一件事。** subject 里出现 `and` 通常是该拆成两个提交的信号
  （`Add X and fix Y` → 拆）。真拆不开时，`and` 后面必须是同一件事的两面。

超长就往下挪。标题行是给 `git log --oneline` 和 GitHub 列表看的，细节属于 body。

---

## 5. body：说「为什么」

subject 与 body 之间**空一行**。每行 ≤ 72 字符（`git log` 默认不折行）。

body 要回答的是代码本身答不了的问题：

- **为什么**要改，而不是改了**什么** —— diff 已经说明改了什么
- 有哪些**约束**：兼容性、上游行为、性能边界、某个 bug 的触发条件
- 排除了哪些**替代方案**，为什么不选
- 有什么**遗留**：还没做完的、刻意留到后续的

不需要 body 的情况：`chore`、纯 `docs` 的错别字修正、依赖小版本升级。
**但只要改动涉及行为、安全、配置默认值，body 就是必填的。**

---

## 6. footer

```
BREAKING CHANGE: <不兼容点，以及调用方要怎么改>
Refs: #123
```

- `BREAKING CHANGE:` 必须顶格写，后面接冒号空格。它会让 semver 工具把主版本号 +1。
- 关联 issue / PR 用 `Refs: #N`；要自动关闭 issue 用 `Closes: #N`。

---

## 7. 语言约定

**subject 用英文，body 中英文皆可。**

理由：近 60 条提交里 38 条已经是英文祈使句，英文是既成事实的主流；Conventional Commits 的
type 关键字本身是英文；`git log --grep` 检索不受输入法与全半角影响。

body 允许中文 —— 解释「为什么」时，用母语写得更准比写得「统一」更重要。
如果团队决定 subject 也改中文，只需要改本节，其余规则不变。

---

## 8. merge 提交与 PR 标题

- **PR 标题就是 merge 提交的 subject**，所以 PR 标题必须符合本规范。
  用 squash merge 时更是如此 —— 那时 PR 标题会成为唯一留下的那条提交信息。
- **不要产生 `Merge branch 'dev' of https://github.com/...` 这种提交。**
  它是 `git pull` 不带 rebase 的副产物。改用：

  ```bash
  git pull --rebase            # 或一次性设成默认：
  git config pull.rebase true
  ```

- 合并 PR 时选哪种方式：**优先 squash**（一个 PR 一条提交，历史干净）；
  若 PR 内每条提交本身都是有意义的独立步骤，用 rebase merge 保留它们。
  **不要用 merge commit**，除非确实要保留分支拓扑。

---

## 9. 提交信息里不许出现的东西

仓库与镜像**均已公开**（见 `本地开发密钥存放规范.md` §1），提交信息和 diff 一样对全网可读、
且同样无法经济地清除。所以：

- ❌ 口令、token、api-key、私钥 —— 包括「只是拿来复现问题」的
- ❌ 生产库连接串、内网地址、客户数据
- ❌ 粘贴的 `.env` / `application-my.yaml` 内容
- ❌ 对具体人的负面评价（提交信息是永久公开的书面记录）

要引用配置项就写占位符形状：`MASTER_DATASOURCE_PASSWORD`，不要写它的值。

CI 的 `No hardcoded credentials` 闸门只扫两份 yaml，**扫不到提交信息** —— 这一条靠自觉。

---

## 10. 写错了怎么改

**还没推送：**

```bash
git commit --amend                    # 改最近一条
git rebase -i HEAD~3                  # 改最近三条（reword / squash / edit）
```

**已经推送，但是你自己的特性分支、且没人在上面接着干活：**

```bash
git rebase -i origin/dev              # 改完
git push --force-with-lease           # 用 --force-with-lease，不要用 --force
```

`--force-with-lease` 会在远端被别人推过时拒绝，`--force` 会直接覆盖掉对方的提交。

**已经推进共享分支（`dev` / `main`）：不要改。** 改写共享历史会让所有已有克隆对不上。
错就错了，在后续提交里说明。

## 11. 提交前自检

```bash
# 1) 最近一条提交的 subject 长度（应 ≤72）
git log -1 --format='%s' | awk '{print length($0)" 字符: "$0}'

# 2) 是否带合法 type 前缀（应有输出）
git log -1 --format='%s' | grep -E '^[a-z]+(\([a-z0-9-]+\))?: ' || echo "!! 缺 type 前缀"

# 3) 待推送的提交里有没有超长 subject 或缺 body 的行为类改动
git log origin/dev..HEAD --format='%h %s' | awk 'length($0)>82 {print "!! 超长: "$0}'

# 4) 提交信息里有没有凭据形状的东西（命中就人工看一眼，不是「必须无输出」）
git log origin/dev..HEAD --format='%B' \
  | grep -nEi '(password|secret|api[-_]?key|token|access[-_]?key)[[:space:]]*[:=][[:space:]]*[^[:space:]$]'
```

第 4 条的判据与 `本地开发密钥存放规范.md` §8 第 1 条一致，只是扫描对象从暂存区换成提交信息。

**它是启发式的，会误报正文里的正常叙述。** 实测：一段 body 只要出现「token」这个词紧跟冒号
和一个值（哪怕那只是在描述一次匿名请求返回了 200），就会被判成凭据。所以它的定位是
「命中了就用眼睛扫一遍」，不是「必须干净」。想彻底消掉误报就得匹配凭据的字符集与长度，
而那会同时漏掉短口令 —— 宁可误报，不要漏报。

写文档或提交信息时要举例，**用占位符或把冒号去掉**，否则自检会先把自己绊倒。
这一条与 `本地开发密钥存放规范.md` §8 第 1 条同源：那边是硬规则（必须无输出），
所以别在 markdown 里写出会被它命中的字面量。

前三条是硬规则，应当全部通过；第四条不是。

## 附：一个完整的好例子

```
fix(system): stop accepting a fixed SMS verification code

application.yaml pinned the code range to 9999~9999, an upstream default kept
for testing convenience, and application-prod.yaml did not override it. Combined
with three @PermitAll endpoints under /system/auth, createSmsCode() inserting
before it sends, and no failed-attempt limit, anyone who knows an admin's mobile
number could obtain a backend token with two POSTs.

Override the range to 1000~9999 in the prod profile so a missing override fails
loudly rather than silently shipping the pinned code.

Still open: SmsCodeServiceImpl has no attempt limit, so the 9000-value space is
brute-forceable within the 10-minute validity window. Closing that needs the
commented-out @RateLimiter in AuthController plus a lockout counter, which
changes behaviour for legitimate users and needs a product decision.
```

subject 57 字符、祈使句、有 type 和 scope；body 第一段讲**为什么这是个洞**（含完整攻击链），
第二段讲**这次修到哪**，第三段讲**还没修什么、为什么没修**。半年后接手的人不需要问任何人。
