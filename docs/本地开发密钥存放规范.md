# 本地开发密钥存放规范

面向：后端负责人，以及所有会在本机跑起 `yudao-server` 的人。
适用范围：本仓库（Star E-Commerce ERP 后端，基于 ruoyi-vue-pro / yudao 的副本，不是 GitHub
意义上的 fork；**仓库与镜像均已公开**，详见 §1）。

---

## 0. 一句话规矩

**仓库里只允许出现占位符，不允许出现真值。**

真值只有三个合法去处：

| 场景 | 存放位置 | 谁负责 |
| --- | --- | --- |
| 本机开发 | 被 `.gitignore` 覆盖的本地文件（见 §3） | 每个开发者自己 |
| CI 服务凭据 | GitHub Actions Secrets；构建不注入应用密钥（见 §5） | 后端负责人 |
| 部署 / 生产运行 | 各 Environment 的 `APP_ENV`，部署时生成主机 `.env`（见 §4） | 后端负责人 |

任何一条真值写进了被 git 跟踪的文件，都按泄露处理，走 §9 的轮换流程 —— 不是「下次注意」。

---

## 1. 为什么现在要立这个规矩

先把暴露面说准，既不夸大也不缩小。以下每条都实测过，**最近一次复核是 2026-10-15**。

**仓库是公开的。** 匿名请求 `api.github.com/repos/Ellean/ruoyi-vue-pro` 返回 **200**，
匿名请求 `branches/dev` 同样 200。所以 **整个 git 历史对全网可读** —— 任何人不需要账号、
不需要 clone，直接调 contents API 就能取到任意历史提交里任意文件的明文。
这是本规范最硬的理由，没有之一。

> 仓库曾是私有的（当时匿名请求返回 404），2026-10-15 转为公开。**这次转变把风险性质改了**：
> 在此之前，历史里的真值只暴露给有仓库权限的人及其克隆；在此之后，暴露给全网。
> 下面「确实发生过的事」那条因此从「内部问题」升级为「公网可读」。

**镜像也是公开的。** `ghcr.io/ellean/ruoyi-vue-pro` 可匿名拉取（实测：匿名取 pull token 后
HEAD manifest 返回 200）。镜像里的 `yudao-server.jar` 打包了全部四份 `application*.yaml`。
也就是说 —— **写进任何一份 `application*.yaml` 的真值，会同时通过仓库历史和镜像两条路公开。**

**确实发生过的事。** 生产 MySQL 的 root 口令在 2026-10-04（`ebb5cdc7c5`）进入仓库，
先后出现在 `tmp_probe_wh.py`、`tmp_probe_wh2.py`、`application-local.yaml`，
2026-10-13 起又进了 `application-prod.yaml`，直到 2026-10-14（`98a8c232b8`）才清除。
删掉行不等于清除，`git log -p` 仍能完整还原。同期还有 XQ RPA 回调 token、
微信公众号/小程序 appid+secret。

**这条现在可以直接验证，而且验证结果是坏的。** 2026-10-15 用**不带任何 token** 的请求实测：

| 匿名请求 | 结果 |
| --- | --- |
| `commits/ebb5cdc7c5` | **200** |
| `contents/yudao-server/src/main/resources/application-local.yaml?ref=ebb5cdc7c5` | **200** |
| `branches/dev` | **200** |

第二行返回 200 意味着**那个含明文 root 口令的文件版本，此刻对全网可读**。
`ebb5cdc7c5` 与 `98a8c232b8` 都在 `origin/dev` 上（也在两个 `ci/*` 分支上），
而公开仓库的所有 ref 都能被匿名 fetch。

**一个已经失效的好消息。** 之前记录过：那次清理（`98a8c232b8`）早于 Dockerfile 首次出现
（`6f2d6b4e74`），所以已发布的镜像里都没含过这个口令。这条**仍然成立**，但在仓库转公开之后
**不再有安慰作用** —— 口令已经通过历史直接暴露了，绕不绕镜像都一样。
（当前镜像内的 `application-prod.yaml` 依然干净，§8 第 4 条无输出。）

**一条更紧急的。** 同期该生产库的 3306 对公网开放，账号是 `root`，口令强度不足。
这一条的严重性原本**不依赖**上面的泄露 ——「公网端口 + root + 弱口令」本身就足够被扫到并爆破。
现在两者叠加了：**公网可达的端口 + 公网可读的口令**。这是 §9 清单里优先级最高的一项，
且已从「待办」变成「窗口正开着」。

结论：真值一旦进了被 git 跟踪的文件，就按已泄露处理，走 §9 轮换。
在仓库公开的前提下，**没有任何豁免空间** —— 「只是本地配置」「只是测试值」「后来删掉了」
都不构成理由，因为历史对全网可读且删不掉。

## 2. 配置是怎么被读到的（改配置前先看懂这段）

`application-prod.yaml` 的每一项都写成 `${环境变量名:默认值}`，例如：

```yaml
password: ${MASTER_DATASOURCE_PASSWORD:}          # 默认空串，部署必填
host:     ${REDIS_HOST:redis}                    # 默认 Compose 内服务名
```

MySQL 安装在宿主机，模板 `MYSQL_HOST=host.docker.internal`；Redis 由各环境 Compose 独立启动，部署必须填写 `REDIS_HOST=redis` 和非空口令，不使用宿主机共享 Redis。

默认值可以**嵌套**，从库整套配置就靠这个机制自动跟随主库，不必重复注入：

```yaml
url:      ${SLAVE_DATASOURCE_URL:${MASTER_DATASOURCE_URL:jdbc:mysql://...}}
password: ${SLAVE_DATASOURCE_PASSWORD:${MASTER_DATASOURCE_PASSWORD:}}
```

**默认值只在对应变量未提供时使用。** `.env` / `APP_ENV` 中的 `KEY=` 是明确空字符串，
不是「使用 Spring 默认值」；不需覆盖的项应注释或删除，从库与派生 URL 尤其如此。

优先级（高 → 低）：

1. 命令行参数 `--key=value`
2. **操作系统环境变量**（生产就走这一层）
3. 外置配置文件 `./config/application-*.yaml`、`./application-*.yaml`
4. classpath 内的 `yudao-server/src/main/resources/application-*.yaml`

第 3 层能盖住第 4 层，是本机开发不改仓库文件就能覆盖配置的关键。

生效的 profile 由 `spring.profiles.active` 决定，仓库默认值是 **`local`**；
镜像里已用 `ENV SPRING_PROFILES_ACTIVE=prod` 把默认改成 `prod`（见 Dockerfile 运行层）。

> **默认值该写什么？** 判据只有一条：漏注入时，应用是**响亮地失败**还是**静默地跑错**。
> 数据库口令默认空串 → Druid 建初始连接池即报错退出，属于响亮失败，可以接受。
> 反过来，把真口令写成默认值 → 漏注入时应用照常起来，连的是生产库，这是最坏的一种。

## 3. 本机开发：真值放哪

### 3.1 首选 —— `application-my.yaml` + `local,my` 双 profile

`.gitignore` 已经忽略了任意层级的 `application-my.yaml`（上游 yudao 的既有约定）。

先在受保护编辑器中准备 `application-my.yaml`，权限设为 `600`，不要覆盖已有文件；编辑器备份和交换文件同样保护。只写需覆盖的项，例如以下**占位内容**，真值不粘贴进 shell heredoc 或命令历史：
```yaml
spring:
  datasource:
    dynamic:
      datasource:
        master:
          username: <local-app-user>
          password: <local-database-password>
  data:
    redis:
      password: <local-redis-password>
```

（AI Key / 模型已统一存库表 `ai_api_key`，不再经 YAML 或环境变量覆盖。）

激活 `local,my` —— 顺序有意义，后出现的 profile 覆盖先出现的：
```bash
./mvnw -pl yudao-server spring-boot:run -Dspring-boot.run.profiles=local,my
```

IDEA 里则在 Run Configuration 的 *Active profiles* 填 `local,my`。

**关键点**：用 `local,my` 而不是单用 `my`。单用 `my` 时 `application-local.yaml` 完全不加载，
你得把它整份抄一遍，之后上游更新也同步不到；双 profile 只需写差异项。

### 3.2 次选 —— 外置 `config/` 目录

不想在 `src/main/resources` 下放文件的话，Spring Boot 的默认搜索路径里有 `./config/`，
优先级高于 classpath。仓库根和 `yudao-server/` 下的 `config/` 都已加进 `.gitignore`：

```bash
mkdir -p config
# 工作目录是仓库根时用 config/，IDEA 以 yudao-server 为工作目录时用 yudao-server/config/
```

### 3.3 也可以 —— 通过运行器注入环境变量

需要环境变量时，由受信任的 IDE / 运行器从本机受保护配置注入；不要在 shell 中写含真值的 `export`、`--password` 或 `docker run -e KEY=真值`。不落盘也不等于保密，进程环境和 Docker env 对特权用户仍可读。

容器化本地运行使用权限 `600` 的 `.env` 与本仓库 Compose，准备方法见部署文档 §4。不要 `source` dotenv 文件。Compose 中的 Redis 不发布端口，服务名 `redis` 也仅在该网络内解析；宿主机 IDEA / Maven 直跑应另配自己的开发 Redis，不能假定 `localhost:6379` 自动连到这个容器。

### 3.4 明确禁止

- ❌ 改 `application-local.yaml` / `application-prod.yaml` 里的值然后提交
- ❌ 在 `application-prod.yaml` 里给任何凭据加「方便一点」的默认值
- ❌ 把真值写进 README、注释、SQL 脚本、单元测试的 `@Test` 常量、CI 的 `env:` 字面量
- ❌ 用 `git add -f` 绕过 `.gitignore`
- ❌ 把 `.env` / `application-my.yaml` 贴到 issue、PR 描述、企微群里排查问题
      （要贴就贴 `key: ${PLACEHOLDER}` 的形状，不贴值）

### 3.5 已知例外

`application-local.yaml` 里保留着上游公开的**微信测试号** appid/secret 与 `root`/`admin` 这类
本地示例口令，与 `origin/master` 逐字节一致。`application.yaml` 里也留着上游的快递查询示例凭据
（`yudao.trade.express.kd-niao.api-key`、`kd100.key`/`customer`）——`yudao-module-mall` 在根 pom
中是注释掉的，这段配置根本不加载。

它们都不是本项目凭据、不连任何真实资源，保留是为了减少与上游的 diff。
**不要**把这条当成「local / 基础配置里可以写真值」的先例 —— 本项目自己的凭据一律走 §3.1–3.3。

## 4. 生产运行：真值放哪

镜像内**不含**任何配置真值。容器只吃环境变量，改配置不重建镜像。

这不是洁癖：真值有**两条**通往公网的路。一是镜像 —— `ghcr.io/ellean/ruoyi-vue-pro` 可匿名拉取，
而 jar 里打包了全部四份 `application*.yaml`；二是仓库本身 —— 已转公开，任何写进被跟踪文件的值
连同它的整个历史都能被匿名读取（见 §1）。已复核当前镜像内的 `application-prod.yaml` 干净，
用 §8 第 4 条可以随时复查。

容器由根目录的 `docker-compose.yml` 起，**仅 app** 的 `env_file` 默认读 `.env`，部署候选阶段由
`APP_ENV_FILE` 指向暂存 env。**部署机上的 `.env` 是 CI 产物，不是日常手工维护的配置**：
应用真值的权威副本在各 GitHub Environment 的单个 secret `APP_ENV` 中；CI 另行加入
`COMPOSE_PROJECT_NAME`、`IMAGE_TAG`、`HOST_PORT`、`CONTAINER_NAME`，并经 SSH 获取 Docker
默认 bridge 的私网 IPv4 写入 `HOST_BIND_IP`。本地默认仅绑定 `127.0.0.1`，CI 不绑定所有接口。
前端 `host.docker.internal` 访问依赖 `host-gateway` 映射、daemon 未改 `host-gateway-ip`，
以及宿主机不向外路由网桥；没有 tailnet 直连 802x 或通知探活链接，探活在 SSH 会话中执行。

宿主机 MySQL 按环境独立建库、使用受限应用账号，不允许远程 root、全局授权或公网 3306。
账号来源须按实际 Compose user-defined subnet 授权，不能把默认 bridge 网段直接当作应用来源；
从 tailnet 与内网的管理访问用独立账号、Host 显式限定来源，不共用应用口令。宿主机 ufw
默认入站 DROP：应用容器、tailnet 与内网到 3306 的入站都要显式放行，规则清单见部署文档 §3.3。
安装、监听配置与初始化的人工步骤见部署文档 §3；装好 MySQL 不代表库表齐全或应用已就绪。

每环境自带 `redis:7.4-alpine`，无主机端口，独立 `redis-data` 卷启用 AOF / `everysec`；
app 等待 Redis `service_healthy`。Redis 只注入 `REDIS_PASSWORD` / `REDIS_PORT`，不读取整份应用 env。
启动时在 tmpfs 写入含口令哈希的 ACL，认证不把明文口令放入命令参数；**宿主机 root / Docker 权限持有者仍能读取容器环境变量**，tmpfs 和哈希不构成对他们的隔离。AOF 不是备份。

落盘与切换：

- runner 用 `umask 077` 创建 env，从生成起权限就是 `600`；远端每次用 `mktemp -d`
  创建独立 `700` 上传暂存目录，而非直接覆盖活动文件。不要另行备份或传播明文副本。
- 远端取得环境目录 `.deploy.lock` 的排他 `flock` 后，验证候选 Compose、`pull app redis`，再执行
  `up -d --pull never --wait --wait-timeout 300 app redis`；分别核对两服务预期镜像 ID 与 `healthy`，
  再验证应用 HTTP 200 和 JSON `status: UP`，才分别用 `mv` 写为活动 `.env` / `docker-compose.yml`。
- 验证失败保留旧活动配置，**但 `up` 可能已替换 app、Redis 并改变运行中的 Redis 口令，不承诺自动回滚**；
  首次失败没有旧配置，用 `docker logs <容器名>` 排查。手动回滚先暂停/等待自动部署并取得同一把锁，
  对两服务一起 pull/up 和验收，核对旧 Redis 的数据兼容性、备份及实际口令，不执行 `down -v`（部署文档 §6）。
- `APP_ENV` 三个环境分别填写，不共用生产凭据；换人接手时审查并轮换访问凭据，
  **字段加密密钥不能直接换**，必须先核对存量数据并按 §7.2 迁移。

以 `.env.example` 的键清单为准，不手敲猜键名。模板有非敏感默认值，密钥真值留空；
**`KEY=` 是显式空串，不需覆盖的项注释或删除**。`XQ_RPA_CALLBACK_BASE_URL` 及第三段不用的
AI 键已注释，以保留默认值；`XQ_ERP_BASE_URL` 已无代码消费者，连同 prod 配置与模板行一起移除。

按部署文档 §4 在本机 `700` 临时目录内用受保护编辑器填写权限 `600` 的文件，用完删除；
不要覆盖已有 `.env`，不要在 shell history、命令参数或聊天中填写真值。先读取现有 Environment
保护配置，现有应用值从授权保管者取得；上传会整份替换，不能漏掉既有功能配置。
```bash
# APP_ENV_PATH 是本机已安全编辑的完整文件绝对路径；ENV 按 dev/test/main 分别设置
gh secret set APP_ENV --repo Ellean/ruoyi-vue-pro --env "$ENV" < "$APP_ENV_PATH"
```
不要用 `gh secret set --env-file` 拆成多个 secret，也不要用含真值的 `--body` 参数。

部署校验只允许模板键（含注释项）和 `JAVA_OPTS`，拒绝重复、未知或编排键，包括
`HOST_BIND_IP`、`APP_ENV_FILE`；非注释内容必须是单行 `KEY=VALUE`。值含 `$` 必须单引号引用，
含空格后的 `#` 也应引用以免截断；不要 `source` 文件。CI 用 `docker compose config --format json`
实际解析，警告或错误均失败，并检查解析后的运行环境：
- `MASTER_DATASOURCE_USERNAME`、`MASTER_DATASOURCE_PASSWORD`、`REDIS_PASSWORD`、`MYBATIS_ENCRYPTOR_PASSWORD` 非空；
- `MYSQL_HOST` 或完整 `MASTER_DATASOURCE_URL` 至少一个；`REDIS_HOST` 必须填写为 `redis`；
- 加密密钥为 **16/24/32 个 UTF-8 字节**；`SERVER_PORT`、`REDIS_PORT` 为 1–65535；`REDIS_DATABASE` 为 0–15。

`REDIS_PORT` 默认 6379，由 app、Redis 监听与健康检查共用；`REDIS_DATABASE` 默认 0。
长度校验不验证存量数据能否解密，操作者必须核实密钥匹配既有数据，不能擅自轮换。
尤其是数据库复制/迁移：仓库基础 SQL 缺 XQ/Quartz，Quartz SQL 含 DROP 和调度状态，
`sync-local-to-prod` SQL 含用户/密钥数据，不可批量导入；后端负责人须提供完整经验证 schema、
脱敏必要种子或批准迁移，保留复制的加密行所匹配的 key。prod Quartz 不自动建表（部署文档 §3.4）。
新增应用变量时同步 YAML 占位符与模板；`JAVA_OPTS` 是镜像入口使用的额外允许项。
修改已有变量的运行值不需重建镜像，新增/修改镜像内 YAML 则需要构建。
本地 Compose 没有 `build` 定义；先拉取 Redis、用 `docker build` 构建 app，运行须加 `up --pull never`，
否则 `pull_policy: always` 会拉取远端 app 镜像。完整命令、主机前置条件与排错见 `docs/部署.md`。

## 5. CI / GitHub Actions

以下是配置核对清单，不代表已在 GitHub 或主机完成验证，也不代替管理员配置。
仓库级项目位于 GitHub → Settings → Secrets and variables → Actions。

**Secrets**（仓库级）

| 名字 | 用途 |
| --- | --- |
| `WECOM_PR_WEBHOOK` | PR 事件的企业微信通知 |
| `WECOM_CI_WEBHOOK` | push / 手动触发的企业微信通知 |
| `TS_OAUTH_CLIENT_ID` | Tailscale OAuth 客户端 ID，deploy 用它把 runner 临时接入 tailnet |
| `TS_OAUTH_SECRET` | 同上的客户端密钥 |
| `DEPLOY_SSH_KEY` | 部署机 SSH 私钥（ed25519 全文，无 passphrase） |

**Secrets**（Environment 级，`main` / `test` / `dev` 各保留一个应用配置 secret）

| 名字 | 用途 |
| --- | --- |
| `APP_ENV` | 按 `.env.example` 填写需覆盖的配置，deploy 验证成功后更新活动 `.env` |

当前工作流只让非 PR 的 `main/test/dev` 分支 push 或 dispatch 进入对应 Environment，
PR 不读取 `APP_ENV`。**这不是「PR 永远无法读环境密钥」的安全保证**：有权改 workflow 的人
可以改环境声明；既有 repo-level SSH/OAuth secrets 也不是 PR 隔离的安全沙箱。

Environment 操作清单：
- 先用 `gh api` 读取三个环境的既有保护和分支规则，保留已有保护再增量调整，不能用新建示例覆盖旧配置；完整命令见部署文档 §3.1。
- `main` 设置 required reviewers、禁止自审，Deployment branches and tags 仅允许 `main` 分支而非同名 tag；发起者不能批准自己的运行，单人场景须找另一位有权限的审阅人，并核对管理员绕过设置。
- `dev`、`test` 分别只允许同名分支，按需增加审批；已有通配符或其他 tag/分支规则须审查后移除。
- 限制仓库写权限、审查 workflow 变更，不把 Environment 审批当成仓库级凭据的隔离边界。
- 合并前先完成 `dev` 的数据库、Redis、Environment / `APP_ENV` 与仓库凭据；`test/main` 在各自首次部署前完成独立准备。PR #8 不自动合并，须由负责人验收并决定。

**Variables**（非机密，可公开；三项均必填）

| 名字 | 示例值 | 用途 |
| --- | --- | --- |
| `DEPLOY_HOST` | `xq-local.tail08f53.ts.net` | 部署目标机 |
| `DEPLOY_USER` | `edward` | 需有 Docker 访问权的部署账号 |
| `DEPLOY_PATH` | `/home/edward/star-ecom-erp-api` | 部署目录 |

规则：

- **构建与测试不需要应用凭据**；测试使用 H2 + jedis-mock + podam，不连真实 MySQL / Redis，
  镜像构建也不注入应用配置。
- 应用凭据只有 `APP_ENV` 一个入口，渲染后上传候选文件；远端退出时清理暂存文件，runner
  always 步骤清理 env 和 SSH 私钥。配置校验成功只报告已验证；错误仅给通用说明、行号或
  已知键名，不回显原行、值或 Compose 解析器输出，也不输出配置内容或键数量。
- PR 检查可被新运行取消，push/dispatch 部署不自动取消；远端 `flock` 排他，回滚同样须持锁。
- 通知 webhook 缺失时 warning 后跳过，不把整跑判红；部署通知不提供探活链接。
- `workflow_dispatch` 也会推镜像，选中非 `main/test/dev` 分支时跳过 deploy；手动触发前确认分支。
- 主机需 Docker Compose >= 2.20、Bash、`flock`、`python3`、`curl` 和部署账号 Docker 访问权；
  宿主机 MySQL 由管理员交互 sudo 安装和初始化，CI 不代装。已有只读观察和仍未完成的步骤见部署文档 §3，不能把主机可 SSH 当成服务已就绪，也不在聊天中发送 sudo 口令。

### 5.1 镜像 tag 规则与分支模型

非 PR 检查通过后推 `:<分支名>` 与 `:<完整 SHA>`；`:latest` 只在 `REF == "main"` 时追加。
分支模型保持 **`dev` 集成、`main` 发布、`test` 预发**；`:latest` 不代表 dev 的最新进度，
不把某一时刻的分支提交差距当成持续有效的部署说明。

deploy 使用完整 SHA tag 定位构建，不部署可变的分支 tag；但 **SHA tag 本身也可被覆盖**，
不能保证不可变或可复现。不可覆盖策略或 digest 固定是后续工作，当前未实现。
`.env` 记录的是最近成功验证的配置；失败时容器可能已被替换，真实运行镜像还须 inspect 核对。
回滚与拓扑见 `docs/部署.md` §1、§6。

## 7. 上游默认值中必须为生产改掉的项

这两条不是「密钥写在哪」的问题，而是上游为**开发方便**留的默认值在生产会变成真实漏洞。
都已经在仓库里处理，列出来是为了让人知道为什么这么改、以及还剩什么没做。

### 7.1 短信验证码被固定成 9999（已修）

`application.yaml` 原本是：

```yaml
yudao:
  sms-code:
    begin-code: 9999 # 这里配置 9999 的原因是，测试方便。
    end-code: 9999
```

`application-prod.yaml` 之前没有覆盖它，于是生产也是 9999。配合下面三个事实，构成一条完整的
未授权登录链：

1. `AuthController` 的 `/system/auth/sms-login`、`/send-sms-code`、`/reset-password`
   三个端点都标了 `@PermitAll`，不需要任何认证；
2. `SmsCodeServiceImpl.createSmsCode()` **先把验证码写库、再调用发送**，且方法没有
   `@Transactional` —— 即使短信通道没配好、发送抛异常，`9999` 这条记录也已经落库；
3. `validateSmsCode0()` 只校验「记录存在 + 未过期（10min）+ 未使用」，**没有失败次数限制**。

于是攻击者只需知道某个管理员的手机号：

```
POST /admin-api/system/auth/send-sms-code   {"mobile":"<目标手机号>","scene":21}
POST /admin-api/system/auth/sms-login       {"mobile":"<目标手机号>","code":"9999"}
→ 拿到该管理员的 access token
```

`/reset-password` 同理，可以直接改口令。

**已做的修复**：`application-prod.yaml` 覆盖为 `begin-code: 1000` / `end-code: 9999`，
恢复成真实随机区间（9000 种取值）。

**还没做的**：`SmsCodeServiceImpl` 没有校验失败次数限制，9000 个取值在 10 分钟有效期内
仍可被暴力枚举。要彻底堵住，需要打开 `AuthController.smsLogin` 上面那段被注释掉的
`@RateLimiter`（上游 issue #851 就是这个），并给验证码校验加失败计数 / 锁定。
这是代码改动且会影响正常用户，需要产品侧拍板，**当前仍是开放项**。

### 7.2 字段加密密钥是上游公开值（部分修）

```yaml
mybatis-plus:
  encryptor:
    password: XDV71a+xqStEA3WH   # 上游公开默认值
```

这个密钥由 `EncryptTypeHandler` 使用，`DataSourceConfigDO.password`
（基础设施 → 数据源配置，管理员登记的外部库口令）落库前用它做 AES 加密。
密钥既然是上游开源仓库里的公开值，**这一列等于没加密** —— 拿到库就能解。

**已做的**：改成 `${MYBATIS_ENCRYPTOR_PASSWORD:XDV71a+xqStEA3WH}`，生产可以注入私有密钥。
默认值必须保留成上游那个值，因为：

- `getEncryptor()` 里是 `Assert.notEmpty(password, ...)`，留空会在首次使用时直接抛异常；
- 换密钥后**已加密的存量行解不开**，`decryptStr` 会失败。

现行 CI 不允许省略或留空 `MYBATIS_ENCRYPTOR_PASSWORD`：必须显式提供 16/24/32 个
UTF-8 字节。**通过长度校验不代表可任意换密钥**；有存量数据时先使用与其匹配的现有密钥，
不能为了首次接入 CI 就生成新值覆盖。YAML 的兼容默认值也不等于已完成私有密钥迁移。

**还没做的（需要一次数据迁移，不能只改配置）**：

1. 生成一个 16 / 24 / 32 个 UTF-8 字节的私有密钥（`SecureUtil.aes` 直接 `getBytes()`，对应
   AES-128/192/256）；
2. 用旧密钥把 `infra_data_source_config.password` 全部读出、明文暂存；
3. 切 `MYBATIS_ENCRYPTOR_PASSWORD` 到新值并重启；
4. 用新密钥重新写回。
   只有确认没有存量加密数据后，才能跳过迁移直接注入新密钥。

**先确认一件事**：生产库里 `infra_data_source_config` 到底有没有数据、存的是哪些库的口令。
如果有，这些口令按已泄露处理，走 §9 轮换。

## 8. 提交前自检

```bash
# 1) 暂存区里有没有「写了真值」的凭据行（命中就人工看一眼）
#    三道过滤缺一不可：跳过 +++ 文件头、跳过新增的注释行、要求分隔符后确实有值。
#    少了第三道，.env.example 里的空凭据占位也会误报 —— 误报会让人
#    不再看这个检查，比没有检查更糟。
git diff --cached -U0 \
  | grep -E '^\+[^+]' \
  | grep -vE '^\+[[:space:]]*(#|\*)' \
  | grep -Ei '(password|secret|api[-_]?key|token|access[-_]?key)[[:space:]]*[:=][[:space:]]*[^[:space:]$#]'

# 2) 有没有 -f 强加了被忽略的文件
git diff --cached --name-only | while read -r f; do
  git check-ignore -q "$f" && echo "!! 被忽略却进了暂存区: $f"
done

# 3) 本机覆盖文件确实没被跟踪。.env.example 是唯一例外 —— 只含占位与非敏感默认值，必须入库。
git ls-files | grep -E 'application-my\.yaml|^\.env|/config/application' | grep -vx '.env.example' \
  && echo "!! 上面这些不该被跟踪"

# 4) 生产会加载的两个文件里，不该再出现非占位符的凭据。
#    注意 application.yaml 是所有 profile 的基线，prod 也会加载它，别只盯 application-prod.yaml。
grep -nE '(password|secret|api-key|access-key[a-z-]*|token):' \
  yudao-server/src/main/resources/application.yaml \
  yudao-server/src/main/resources/application-prod.yaml \
  | grep -v '\${' \
  | grep -v 'cb022f1e-48f1-4c4a-a723-9001ac9676b8'  # 上游快递查询示例 key，配置不加载，见 §3.5

# 5) 上游为「测试方便」留的危险默认值，生产必须已被覆盖（下面两条都应当有输出）
grep -nE '^[[:space:]]+(begin-code|end-code):' yudao-server/src/main/resources/application-prod.yaml
grep -n 'MYBATIS_ENCRYPTOR_PASSWORD' yudao-server/src/main/resources/application.yaml
```

预期结果：

- 第 1、3、4 条 **无输出**。第 4 条已经挂进 CI 的 Build 腿（step 名 `No hardcoded credentials`），
  违反即整跑判红；这里列出来是为了本地提交前能先自查，不必等 CI。
- 第 1 条有一个**已知盲区**：带引号的空字符串值（`password` 后面跟一对空的双引号）会被
  当成真值报出来。这是刻意的取舍 —— 反过来放宽就会漏掉引号里裹着真口令的写法。
  宁可偶尔误报一条。注意本条会扫所有暂存文件，**包括 markdown**：往文档里写形如
  `键名: 值` 的示例时，用占位符或留空，否则自检会先把自己绊倒。
- 第 5 条 **有输出**，分别对应 §7.1 和 §7.2 的修复。哪天它变成空输出，说明覆盖被回退掉了。
- 第 4 条有一个**已知漏网**：它靠 `grep -v '\${'` 放过占位符，因此看不见「占位符里塞了真默认值」
  这种写法。目前全仓只有一处，就是 §7.2 的 `${MYBATIS_ENCRYPTOR_PASSWORD:XDV71a+xqStEA3WH}`，
  且是刻意保留的（留空会 `Assert.notEmpty` 抛异常）。**新增这种写法一律视为违规。**
- 第 4 条的排除项只有一个，且必须是可论证「配置根本不加载」的上游示例值。
  往这行后面继续追加 `grep -v` 之前，先想清楚是不是应该改掉源头。

依赖升级，不要混进 CI / 配置类改动里。**
