# 部署

后端自己的 CI/CD：构建镜像 → 推 GHCR → 经 tailnet SSH 到部署机 → `docker compose up -d` → 探活。
与前端仓库（`yudao-ui-admin-vben`）完全解耦，前端只通过一个 nginx 反代地址感知后端。

架构蓝本与取舍见前端仓库的 `docs/springboot-deploy.md`；本文只写**本仓库的实际状态与操作步骤**。
密钥存放的规矩见 `docs/本地开发密钥存放规范.md`。

---

## 1. 拓扑

三个分支各起一份独立的 compose project，容器 / 网络 / 卷 / 端口完全隔离，同一台机器上并存。

| 分支 | 宿主机端口 | compose project | 容器名 | 服务器目录 |
| --- | --- | --- | --- | --- |
| `main` | 8020 | `star-ecom-erp-api-main` | `star-ecom-erp-api` | `/home/edward/star-ecom-erp-api/main` |
| `test` | 8021 | `star-ecom-erp-api-test` | `star-ecom-erp-api-test` | `/home/edward/star-ecom-erp-api/test` |
| `dev` | 8022 | `star-ecom-erp-api-dev` | `star-ecom-erp-api-dev` | `/home/edward/star-ecom-erp-api/dev` |

容器内端口固定 **48080**（`application-prod.yaml` 的 `SERVER_PORT` 默认值），宿主机端口段
8020-8022 避开前端的 8010-8012。前端 nginx 经 `host.docker.internal:802x` 反代过来。

**不开 Tailscale Funnel。** 后端全量接口（Swagger、Druid、actuator）直接挂公网不是我们要的，
前端同源反代已覆盖浏览器需要的全部路径。tailnet 内仍可直连 `http://<host>:802x`，
CI 的探活走的就是这条路。要开的话参照 `springboot-deploy.md` §2.4 加 sidecar。

## 2. 流水线

```text
push main/test/dev ─┐
                    ├─→ checks（matrix，fail-fast）
PR（任意目标分支） ─┘     ├─ Build         （runner 侧编译，兼跑硬编码凭据闸门）
                          ├─ Test          （H2 + jedis-mock，纯内存）
                          └─ Docker Build  （只构建不推送，写 GHCR buildcache）
                               ↓
                          ci-ok（聚合判定）
                               ↓  仅非 PR 事件
                          push-image（推 :<分支> + :<sha>；main 额外推 :latest）
                               ↓  仅 push 到 main/test/dev
                          deploy（入 tailnet → 渲染 .env → SSH → pull/up -d → 探活）
                               ↓
                          notify（企微，部署成功时附探活地址）
```

PR 运行止于 `ci-ok`：**不推镜像、不部署、也拿不到部署密钥**（`deploy` 挂 `environment`，
PR 不挂环境）。

部署机上的 `docker-compose.yml` 与 `.env` 每次部署被 CI 覆盖同步，**仓库是 compose 文件的
唯一事实源**，不要在服务器上手改 compose。

## 3. 一次性配置

### 3.1 GitHub Environments（**必须做，否则 deploy 会 fail-fast**）

Settings → Environments → New environment，建三个：`main`、`test`、`dev`（名字必须与分支名
完全一致，deploy 靠 `environment: ${{ github.ref_name }}` 挂接）。

每个环境各配一个 secret：

| 名字 | 值 |
| --- | --- |
| `APP_ENV` | 一份**填好真值**的 `.env.example`，见 §4 |

三个环境各填各的（数据库、Redis、对外地址通常不同）。没配 `APP_ENV` 时 deploy 会在
「Render runtime .env」这一步直接红掉，不会把配置不全的容器起起来。

**建议同时给 `main` 环境加 required reviewers**（Environment → Required reviewers）。
`dev` 分支没有分支保护，任何有写权限的人推一个提交就会触发一次 dev 部署；`main` 加上审批
之后，「CI 一绿就自动碰生产」这条路才算堵住。要不要给 `test`/`dev` 也加是取舍问题：
加了每次部署都要人点一下，不加则写权限等同于部署权限。

### 3.2 仓库级 Secrets / Variables（已配好，列出来备查）

| 类型 | 名字 | 用途 |
| --- | --- | --- |
| Secret | `TS_OAUTH_CLIENT_ID` / `TS_OAUTH_SECRET` | CI 临时节点入网（与前端仓库同一对） |
| Secret | `DEPLOY_SSH_KEY` | 部署机 SSH 私钥（ed25519 全文，无 passphrase） |
| Secret | `WECOM_PR_WEBHOOK` / `WECOM_CI_WEBHOOK` | 企微通知（标题自报「后端」） |
| Variable | `DEPLOY_HOST` | `xq-local.tail08f53.ts.net` |
| Variable | `DEPLOY_USER` | `edward`（需在 docker 组） |
| Variable | `DEPLOY_PATH` | `/home/edward/star-ecom-erp-api` |

`DEPLOY_HOST` / `DEPLOY_USER` 缺失时 deploy 直接报错中止，不会静默跳过。

### 3.3 Tailscale

- ACL 里 `tag:github-actions-xq` 的 `tagOwners` 已存在（前端配过），**无需改动**。
- 因为不开 Funnel，**不需要** `TS_AUTHKEY`，也不需要新节点和 `nodeAttrs.funnel`。
- CI 节点是 ephemeral 的，job 结束自动离网。

### 3.4 部署机

- Docker + compose plugin、`edward` 在 docker 组、docker.io 可达 —— 前端部署时已就绪。
- 部署目录由 CI 自动创建。
- 宿主机上要有后端能连到的 MySQL 与 Redis。`application-prod.yaml` 里 `MYSQL_HOST` /
  `REDIS_HOST` 的默认值就是 `host.docker.internal`，compose 已加 `host-gateway`，
  所以「数据库与后端同机」这种布局不用额外配置。
- 确认宿主机防火墙对 docker 网桥放行 8020-8022（前端 nginx 要从容器里连过来），
  但**不要**把这几个端口放行到公网。

## 4. `APP_ENV` 怎么写

它就是 `.env.example` 填上真值后的整份内容。键名清单、分档与默认值全在 `.env.example` 里，
不要凭记忆敲。

```bash
cp .env.example /tmp/app-env && chmod 600 /tmp/app-env && $EDITOR /tmp/app-env
# 填完后整份粘进 GitHub Environment secret APP_ENV，然后销毁本地副本
shred -u /tmp/app-env 2>/dev/null || rm -f /tmp/app-env
```

deploy job 会先校验再落盘，以下情况会红掉：

- 有非注释、非空行不是 `KEY=VALUE` 形状（报错只回显首字段，值一律抹掉，不会写进日志）
- 出现了 `COMPOSE_PROJECT_NAME` / `IMAGE_TAG` / `HOST_PORT` / `CONTAINER_NAME`
  —— 这四个由 CI 按分支计算，覆盖它们会让三个环境的编排互相踩
  （`SERVER_PORT` 不在其列：compose 的端口映射与镜像的 `HEALTHCHECK` 都跟着它走，改了不会失配，
  但换环境本来只该动 `HOST_PORT`）
- `MYSQL_HOST` / `MASTER_DATASOURCE_PASSWORD` / `REDIS_HOST` 缺失或值为空

几个坑：

- **值里有 `#` 要小心。** compose 的 `env_file` 按 dotenv 规则解析，`#` 前面有空白就会被
  当成行内注释截断。口令含 ` #` 的话请用引号包起来，或干脆别用这个字符。
- **留空的键会回落到 yaml 默认值**，而默认值是按「漏注入就响亮地失败」设计的。所以
  「起不来」通常不是 bug，是某个必填项没填。
- 想改的项 yaml 里没有占位符？先去 `application-prod.yaml` 加 `${VAR:default}`，
  同时给 `.env.example` 补一行（双向对齐，见密钥规范 §4）。

## 5. 本地跑

```bash
cp .env.example .env && chmod 600 .env && $EDITOR .env
docker compose up -d          # 拉 GHCR 上的 :dev（公开镜像，不用登录）
docker compose logs -f app
```

本地从零构建（不走 GHCR）：`docker compose build` 需要先有一个 `IMAGE_TAG` 指向本地镜像，
或直接 `docker build -t ghcr.io/ellean/ruoyi-vue-pro:dev .` 再 `up -d`。

`.env` / `.env.*` 已被 gitignore（`.env.example` 是唯一例外），`git check-ignore -v .env`
可以随时复查。

## 6. 回滚

`push-image` 同时推 `:<分支>` 和 `:<完整 sha>` 两个 tag，但**部署用的是 sha tag** ——
分支 tag 是可变的，部署机上一次手动 `docker compose pull` 就会悄悄换成别的构建；sha tag
让 `cat .env` 直接说明线上跑的是哪一次构建。

回滚：

```bash
ssh edward@xq-local.tail08f53.ts.net
cd /home/edward/star-ecom-erp-api/dev
grep IMAGE_TAG .env                       # 看当前是哪次构建
sed -i 's/^IMAGE_TAG=.*/IMAGE_TAG=<历史 sha>/' .env
docker compose pull && docker compose up -d
```

下一次 CI 部署会把 `IMAGE_TAG` 覆盖回新的 sha，这是预期行为。

## 7. 排错

| 现象 | 先看 |
| --- | --- |
| deploy 红在 `Render runtime .env` | Environment `APP_ENV` 没配，或形状/必填项不合规，报错信息里写了具体是哪条 |
| deploy 红在 `Resolve deploy target` | 仓库 variable `DEPLOY_HOST` / `DEPLOY_USER` 缺失 |
| deploy 红在 `Deploy over SSH`，`Permission denied` | `DEPLOY_SSH_KEY` 与部署机 `~/.ssh/authorized_keys` 不匹配，或 `edward` 不在 docker 组 |
| deploy 红在 `Verify over tailnet` | 容器起了但没 UP。SSH 上去 `docker compose logs app`：多半是数据库/Redis 连不上（配置错或宿主机端口没放行），冷启动也确实慢，探活窗口是 300s |
| 探活通了但前端 API 全 502 | 前端 `BACKEND_UPSTREAM` 还指着旧地址，见 §8 |
| 容器反复重启 | `docker compose logs app`。Druid 建连接池失败会直接退出，这是「口令没注入」的设计行为 |

探活地址（tailnet 内）：`http://xq-local.tail08f53.ts.net:8022/actuator/health`（dev）。
`/actuator/**` 是 `permitAll`（`yudao-module-infra` 的 `SecurityConfiguration`），不用带 token；
prod 只暴露 `health,info`，Druid 控制台是关的。

## 8. 与前端仓库的衔接

前端 nginx 把 `/admin-api`、`/infra/ws`、`/actuator/health`、`/doc.html` 等路径反代到
`BACKEND_UPSTREAM`。当前它仍指向 co-located 的旧后端 `host.docker.internal:48080`。

后端某环境 `docker compose ps` 健康之后，切换动作在前端仓库：改 `.github/workflows/ci.yml`
deploy job 里对应分支 case 的 `BACKEND_UPSTREAM` 为 `host.docker.internal:802x` → 合并 →
自动部署生效。**只影响运行时反代，不需要重建任何镜像。**

切换后浏览器验证：登录 + 任一 API 页 + `/doc.html` + IM websocket。

## 9. 已知未决项

- **`main` 落后 `dev`。** `main` 停在 `cd4e416c38`（2026-09-29），所以 `:main` / `:latest`
  指向的是一棵旧树。在 `dev` 合并进 `main` 之前，别指望 `main` 环境部署出的是最新代码；
  部署用 sha tag 正是为了让这件事在 `.env` 里一眼可见。
- **凭据的存放位置是一次策略选择。** 现在的模型是「运行期配置放在 GitHub Environment
  secret `APP_ENV` 里，由 deploy job 渲染成部署机上的 `.env`」，与前端仓库一致。代价是
  凭据在 GitHub 上多存了一份，且 `dev` 无分支保护 —— 有写权限的人可以改 workflow 把它读走。
  另一种模型是「凭据只存在部署机上，CI 只写编排键」，能少一份副本，但服务器状态就不在任何
  版本控制里了。要收紧，优先给 `main` 加 required reviewers（§3.1）。
- **每次部署都要重拉 386MB。** `:dev` 压缩后 511MB、10 层，其中 fat jar 单独占 386MB，
  而 Dockerfile 是用一条 `COPY` 把它放进镜像的 —— 改一行 Java 代码这一层就失效，部署机
  就得重下 386MB。治法是把 `yudao-server` 打成分层 jar（Spring Boot `layertools`），
  依赖层与代码层分开，日常部署只重下几百 KB 的代码层。**这是一次独立的构建改造，
  不要混进部署链路里。**
- **短信验证码没有失败次数限制**，`MYBATIS_ENCRYPTOR_PASSWORD` 的轮换需要数据迁移 ——
  两项都记在 `docs/本地开发密钥存放规范.md` §7、§9。
