# 部署

本文以 `.github/workflows/ci.yml`、`docker-compose.yml`、`.env.example` 为准；密钥规范见 `docs/本地开发密钥存放规范.md`。
后端独立构建并推送 GHCR，经 Tailscale 网络 SSH 部署，前端通过 nginx 反代访问。

## 1. 拓扑与网络边界

三个分支使用独立 Compose project，容器、网络、卷和宿主机端口分开；目录为 `<DEPLOY_PATH>/<分支>`。

| 分支 | 宿主机端口 | Compose project | 容器名 |
| --- | --- | --- | --- |
| `main` | 8020 | `star-ecom-erp-api-main` | `star-ecom-erp-api` |
| `test` | 8021 | `star-ecom-erp-api-test` | `star-ecom-erp-api-test` |
| `dev` | 8022 | `star-ecom-erp-api-dev` | `star-ecom-erp-api-dev` |

容器内 `SERVER_PORT` 默认 48080，端口映射与镜像健康检查随它变化。
- 本地 Compose 默认仅绑定 `127.0.0.1`；CI 经 SSH 查询 Docker 默认 `bridge` 网关，校验为私网 IPv4 后写入 `HOST_BIND_IP`。
- 不再绑定 `0.0.0.0`，不提供 tailnet 直连 802x 或通知探活链接；健康检查在 Tailscale 网络内的 SSH 会话中执行。
- 前端仍可通过 `host.docker.internal:802x` 访问，前提是前端配置了 `host-gateway` 映射、Docker daemon 未改 `host-gateway-ip`，且宿主机不向外路由网桥。跨网络的发布端口走 Docker DNAT 转发，不经过 ufw INPUT（本机 8012 互探实测），因此不需要 ufw 放行。
- 不开 Tailscale Funnel；802x 只绑定网桥网关，不接受 tailnet / 内网直连，也不向公网开放。

MySQL 安装在宿主机，每个环境单独建库、建受限应用账号；监听回环、Docker 网关，并绑定 tailnet 与内网地址供管理访问（§3.3），不开放公网 3306。
宿主机 ufw 已启用且默认入站 DROP（本机实测）：宿主机进程端口（如 MySQL 3306）对容器 / tailnet / 内网的入站必须显式放行（§3.3 防火墙小节）；Docker 发布的端口不受 ufw INPUT 控制，暴露面由 `HOST_BIND_IP` 收敛。
Redis 由同一 Compose project 启动，镜像为 `redis:7.4-alpine`，**不发布宿主机端口**；应用通过服务名 `redis` 连接，等待 Redis `service_healthy` 后启动。
每个 project 的 `redis-data` 卷独立，启用 AOF、`appendfsync everysec`；这不是备份，异常断电仍可能丢失最近约一秒写入。
Redis 容器只接收 `REDIS_PASSWORD` / `REDIS_PORT`，不加载整份应用 env。启动时在 tmpfs 生成含口令哈希的 ACL，不把明文口令放进命令参数；**Docker 环境变量仍可被宿主机 root / 有 Docker 权限者读取**。

## 2. 流水线与失败语义

`checks（Build / Test / Docker Build）→ ci-ok → push-image → deploy → notify`。
PR 仅检查并通知，不推镜像、不部署；非 PR 检查通过后推镜像，deploy 仅允许 `main/test/dev` 分支的 push 或手动 dispatch。
并发组按 workflow/ref 划分：新 PR 运行可取消旧检查，push/dispatch 部署不因新运行而自动取消。

部署顺序：
1. 读取对应 Environment 的 `APP_ENV`，生成并校验候选 `.env.deploy`（规则见 §4）。
2. 经 SSH 获取网桥 IP；每次用 `mktemp -d` 创建独立的 700 上传暂存目录，env 从生成起就是 600。
3. 远端通过环境目录的 `.deploy.lock` 执行排他 `flock`（最多等 600 秒），持锁验证候选 Compose 配置并 `pull app redis`。
4. 使用候选文件运行 `up -d --pull never --wait --wait-timeout 300 app redis`，分别核对 app、Redis 容器镜像 ID 等于本次拉取镜像的预期 ID、健康状态为 `healthy`。
5. 在 SSH 会话内请求网桥地址的 `/actuator/health`，要求 HTTP 200 且 JSON `status` 为 `UP`；通过后才分别用 `mv` 将 env 和 compose 写为活动 `.env`、`docker-compose.yml`。
6. 远端脚本退出时清理暂存文件；runner 的 always 清理步骤删除 env 和 SSH 私钥。通知只报告结果和运行入口。

**验证失败保留旧活动配置，但 `up` 可能已经替换 app、Redis，甚至改变运行中的 Redis 口令，不承诺自动回滚。** 两次 `mv` 也不是跨文件事务，旧 `.env` 不一定反映运行状态。
首次部署失败没有旧活动配置可回滚，应按容器名查看日志再修复重试（§7）。流程不执行全局 image prune 或 `--remove-orphans`，日常部署和回滚都不要执行 `down -v`。
仓库是 Compose 的事实源；正常配置变更改仓库/Environment 后重新部署，不在服务器长期手改编排。

## 3. 合并前操作清单

以下命令由管理员执行，不代表本文已执行配置或部署。**PR #8 不自动合并**：先完成宿主机 MySQL、经确认的数据库初始化、`dev` 的 Environment / `APP_ENV` 和仓库凭据，再由负责人审查检查结果并决定合并。`test`、`main` 的独立数据库、账号和应用密钥可在各自首次部署前完成；`main` 的审批与分支限制也必须先就绪，不能先部署再补保护。

### 3.1 GitHub Environments

- 创建 `main`、`test`、`dev`，每个环境只存一个应用配置 secret：`APP_ENV`；三个环境分别填写，不共用生产凭据。
- `main` 必须设置 required reviewers，禁止发起者自审，Deployment branches and tags 只允许 `main` **分支**。只有一个操作者时，禁止自审会阻止其批准自己的部署；应指定另一位有权限的审阅人，而不是临时移除保护。
- `dev`、`test` 的部署分支规则分别仅匹配同名分支；是否增加审批另行决定。
- 限制仓库写权限并审查 workflow 变更：当前工作流在 PR 不读取 `APP_ENV`，但能修改 workflow 的人可以改环境声明，不能据此声称 PR 永远无法读取环境密钥。
- 既有 repo-level SSH/OAuth secrets 不是 PR 隔离的安全沙箱，Environment 审批不能替代仓库权限控制。

在可信本机使用已获仓库管理权限的 `gh`（下例另需 `jq`）。**任何更新前先读取既有环境和保护规则**，输出只有配置元数据，不含 secret 值：
```bash
REPO=Ellean/ruoyi-vue-pro
gh auth status
gh api "repos/$REPO/environments"
for ENV in dev test main; do
  gh api "repos/$REPO/environments/$ENV"
  gh api "repos/$REPO/environments/$ENV/deployment-branch-policies"
  gh secret list --repo "$REPO" --env "$ENV"
done
gh secret list --repo "$REPO"
gh variable list --repo "$REPO"
```
只有确认权限正常且环境确实不存在时，404 才按「待创建」处理。已存在的环境须保留原审阅人、等待时间、自审/管理员绕过设置和自定义保护规则，在 Settings → Environments 逐项补齐；**不要用下面的新建 PUT 覆盖现有环境**。

以下仅创建已确认不存在的环境，按实际缺项执行；不要整段重复运行：
```bash
# 仅当 dev、test 均不存在时运行此循环；否则只创建缺失的那个
for ENV in dev test; do
  gh api --method PUT "repos/$REPO/environments/$ENV" --input - <<'JSON'
{"deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}
JSON
done

# 仅当 main 不存在时；替换为实际审阅人 GitHub 登录名（需具备仓库访问权限）
REVIEWER_LOGIN='<reviewer-login>'
REVIEWER_ID=$(gh api "users/$REVIEWER_LOGIN" --jq .id) || exit 1
jq -n --argjson id "$REVIEWER_ID" '{
  reviewers: [{type: "User", id: $id}],
  prevent_self_review: true,
  deployment_branch_policy: {protected_branches: false, custom_branch_policies: true}
}' | gh api --method PUT "repos/$REPO/environments/main" --input -
```
确认各环境已启用 custom branch policies 后，给缺少规则的环境添加唯一同名 **branch** 规则（非 tag）；已有正确规则不重复 POST：
```bash
# 仅在三个环境都尚无此规则时运行循环；否则逐个补缺项
for ENV in dev test main; do
  gh api --method POST "repos/$REPO/environments/$ENV/deployment-branch-policies" \
    -f name="$ENV" -f type=branch
done
```
若读取结果含其他分支、通配符或 tag 放行规则，应审查后逐条移除，而非只追加规则；可在 Settings 中操作，或用下面的已核对 ID：
```bash
ENV=dev                       # 按目标环境调整
POLICY_ID='<reviewed-policy-id>'
gh api --method DELETE "repos/$REPO/environments/$ENV/deployment-branch-policies/$POLICY_ID"
```
配置完重跑读取命令，确认三个环境各仅同名 branch，`main` 审阅人与禁止自审生效；同时审查管理员可否绕过保护，不把 required reviewers 描述成不可绕过的权限边界。`APP_ENV` 的整文件上传见 §4。

### 3.2 仓库 Secrets / Variables

| 类型 | 名字 | 用途 / 配置示例 |
| --- | --- | --- |
| Secret | `TS_OAUTH_CLIENT_ID` / `TS_OAUTH_SECRET` | runner 加入 tailnet |
| Secret | `DEPLOY_SSH_KEY` | 部署账号 SSH 私钥（无 passphrase） |
| Secret | `WECOM_PR_WEBHOOK` / `WECOM_CI_WEBHOOK` | 企微通知；缺失时跳过通知 |
| Variable | `DEPLOY_HOST` | 例如 `xq-local.tail08f53.ts.net` |
| Variable | `DEPLOY_USER` | 例如 `edward` |
| Variable | `DEPLOY_PATH` | 例如 `/home/edward/star-ecom-erp-api` |

三项部署变量都必填。确认 OAuth 可使用 `tag:github-actions-xq` 且网络策略允许 SSH；本流程不需要 `TS_AUTHKEY` 或 Funnel 配置。
先读 §3.1 的现有值，确认后才更新（以下是操作示例，不是执行记录）：
```bash
gh variable set DEPLOY_HOST --repo "$REPO" --body 'xq-local.tail08f53.ts.net'
gh variable set DEPLOY_USER --repo "$REPO" --body 'edward'
gh variable set DEPLOY_PATH --repo "$REPO" --body '/home/edward/star-ecom-erp-api'
# 仅对确认缺失或需轮换的 secret 操作；真值来自本机权限 600 的文件
SECRET_NAME=DEPLOY_SSH_KEY       # 其他仓库 secret 按上表逐个处理
SECRET_FILE='<absolute-path-to-protected-secret-file>'
gh secret set "$SECRET_NAME" --repo "$REPO" < "$SECRET_FILE"
```
不要把口令、私钥或 OAuth secret 放在 `--body` 参数、终端粘贴脚本、日志或聊天里。GitHub 只能列出 secret 元数据，不能读回原值；已有密钥须从授权保管者处取得，不因无法读取而盲目覆盖。

### 3.3 宿主机安装 MySQL（管理员交互执行）

已有只读检查确认（最近一次复核 2026-10-15）：`edward@xq-local.tail08f53.ts.net` 可 SSH 登录，系统是 Ubuntu 26.04 x86_64，Docker 29.8.1 / Compose 5.5.1；MySQL 8.4.11 已安装并 active+enabled，`bind-address` 为 `127.0.0.1,172.17.0.1`、`mysqlx-bind-address` 为 `127.0.0.1`，drop-in 已含 `Requires/After=docker.service`；**尚未初始化任何本项目数据库**。默认 bridge 网关为 `172.17.0.1`、网段为 `172.17.0.0/16`，前端已有 host-gateway 映射。`edward` 的 `sudo -n` 需要交互口令。

三个实测结论决定后续步骤：
- 宿主机 ufw active、默认入站 DROP：从 `bridge` 与 `star-ecom-erp-dev_default` 探测 `172.17.0.1:3306/6379` 均超时（被丢弃）→ 应用容器连 MySQL 必须先加放行规则（见下文 ufw 小节）。
- 从 tailnet 探测 `100.73.52.43:3306` 返回 RST（未被丢弃，只是无监听）→ tailnet 路径本身可达；MySQL 绑定 tailnet 地址后即可连接。
- 从 `bridge` 网络探测已发布的 `172.17.0.1:8012` 可连通、同网络内探测超时 → Docker 发布端口经 DNAT 转发不经过 ufw INPUT，与宿主机进程端口的防火墙语义不同。

当前主机已完成安装：可跳过下面的安装与首装检查，直接从绑定修改（`sudoedit …mysqld.cnf`）与 systemd 依赖补全开始；安装步骤保留供重装 / 其他环境使用。

不能由无 sudo 凭据的自动化代装；请有权限的操作者在自己终端交互输入 sudo 口令，不在聊天中发送，不用 Docker 特权容器绕过 sudo。

**先检查再安装。** 其他主机可能已有数据、定制 datadir 或容器数据库，遇到现有实例先确认负责人和备份，不覆盖配置、不初始化已有数据目录：
```bash
ssh edward@xq-local.tail08f53.ts.net
sudo -v                         # 在当前终端交互认证
lsb_release -ds
dpkg-query -W mysql-server mysql-server-8.4 mariadb-server
apt-cache policy mysql-server
sudo ls -ld /var/lib/mysql /etc/mysql
sudo systemctl status mysql mariadb --no-pager
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
sudo ss -lntp
```
缺包、缺目录、缺服务时部分命令会非零退出；若发现现有配置，用 `sudo less /etc/mysql/mysql.conf.d/mysqld.cnf` 等检查其 include 和 datadir，不能只凭标准目录不存在就断言没有数据。

确认可安装后使用 Ubuntu 自带源的 MySQL 8.4，无需第三方 APT 仓库：
```bash
sudo apt update
apt-cache policy mysql-server   # 确认候选来源和 8.4 版本；异常则停止
sudo apt install mysql-server
mysql --version
docker network inspect bridge --format '{{range .IPAM.Config}}{{.Gateway}} {{.Subnet}}{{end}}'
sudoedit /etc/mysql/mysql.conf.d/mysqld.cnf
```
在现有 `[mysqld]` 段中核对并修改以下项，保留其他配置，检查其他 include 文件是否覆盖它们。MySQL 8.4 支持逗号分隔的多地址绑定；`0.0.0.0` / `*` 一律不用。四个地址分别对应回环、Docker 默认 bridge 网关、tailscale0 与内网网卡，全部替换为实际值（取值：`ip -4 addr show`、`tailscale ip -4`）：
```ini
[mysqld]
bind-address = 127.0.0.1,172.17.0.1,100.73.52.43,192.168.1.104
mysqlx-bind-address = 127.0.0.1
```
**任一枚举的地址在本机不存在，mysqld 会拒绝启动**（不是跳过该项）。因此：
- 内网地址若由 DHCP 分配，须在路由器侧做地址保留，否则换 IP 后 MySQL 启动失败或绑定漂移；
- tailnet 地址随节点稳定，但重装 / 注销 tailscale 后会变，届时同步更新此处；
- tailnet 访问用 IPv4（`100.x`）地址；未绑定 tailnet IPv6（ULA），客户端若优先 IPv6 会失败，显式加 `-4` 或指定 `100.x` 地址。
MySQL 监听 Docker 网关与 tailscale0 地址时，启动必须等 bridge 与 tailscale0 就绪。先检查现有 unit / drop-in，再通过 systemd 编辑器合并依赖，不覆盖整个 unit：
```bash
sudo systemctl cat mysql.service
sudo systemctl edit mysql.service
```
在 drop-in 的有效编辑区域把依赖补全为：
```ini
[Unit]
Requires=docker.service
Wants=tailscaled.service
After=docker.service tailscaled.service
```
`After=` 是列表设置，写在 drop-in 会与 unit 既有值合并，不要整段清空重置。标准 Docker daemon 启动完成会建立默认 bridge；tailscaled 为 notify 型服务，就绪时 tailscale0 地址已配置，若仍有瞬时竞态，mysqld 会因缺地址退出并由 `Restart=on-failure` 重试。用 `Wants`（而非 `Requires`）避免 tailscale 维护时把 MySQL 一并拖停；代价是 tailscaled 启动失败时 mysqld 会退出重试，属响亮失败。此依赖会耦合 MySQL 与 Docker：停止 Docker 可能连带停止 MySQL，维护后检查并启动 MySQL；安排可控重启验证，不假定仅重启容器就够。
```bash
sudo systemctl daemon-reload
sudo systemctl enable docker.service mysql.service
sudo systemctl restart mysql.service
sudo systemctl status mysql.service --no-pager
sudo ss -lntp 'sport = :3306 or sport = :33060'
sudo env MYSQL_HISTFILE=/dev/null mysql
```
在交互 mysql 中检查 `SHOW VARIABLES WHERE Variable_name IN ('bind_address','mysqlx_bind_address','datadir');`，退出后核对 3306 监听出现在四个地址（回环、网桥、tailnet、内网）、33060 仅回环。随后按下面的 ufw 小节放行，再从各来源实测。

#### 宿主机防火墙（ufw）

ufw 处于 active、默认入站 DROP（实测）：容器到宿主机进程端口被直接丢弃；tailnet 路径因 tailscale 自插规则当前可达，但仍按下文显式固化。只放行必要来源，保留已有规则，逐条追加：
```bash
sudo ufw status numbered
# 各环境应用容器 → 宿主机 MySQL；源为对应 star-ecom-erp-api-<env>_default 网段的实际 subnet（§3.4 查询）
sudo ufw allow from <env_app_subnet> to 172.17.0.1 port 3306 proto tcp
# tailnet 管理访问（实测已可达，显式落规则固化，避免依赖 tailscale 自插规则的相对顺序）
sudo ufw allow in on tailscale0 to 100.73.52.43 port 3306 proto tcp
# 内网管理访问；源为宿主所在网段
sudo ufw allow from 192.168.1.0/24 to 192.168.1.104 port 3306 proto tcp
```
- 不要放行 3306 到公网，也不要为排障临时写成不带来源的 `allow 3306`；`mysqlx`（33060）保持仅回环，不需要放行。
- 8020–8022 不需要 ufw 规则：Docker 发布端口走 DNAT 转发，不经过 ufw INPUT（8012 互探实测）；暴露面由 `HOST_BIND_IP=172.17.0.1` 收敛，tailnet / 内网无法直连 802x。阶段 6 前端切换若实测不通，先复查 §1 的网络前提，再考虑 DOCKER-USER 层规则，而不是放宽 INPUT。
- 每条规则生效后从对应来源实测：应用容器内 `mysql -h host.docker.internal -u <env-user> -p`（§3.4）；Mac 侧 `nc -zv -w 3 100.73.52.43 3306`；LAN 机器 `nc -zv -w 3 192.168.1.104 3306`。

### 3.4 独立账号、实际网段与数据库初始化

每环境使用独立库和非 root 应用账号，例如 `star-ecom-dev` / `star_dev`、`star-ecom-test` / `star_test`、`star-ecom-main` / `star_main`。**MySQL 监听的目标网关不等于客户端来源网段**：Compose 使用 user-defined network，不能直接拿 `172.17.0.0/16` 授权。

在宿主机检查实际环境网络：
```bash
docker network ls --filter label=com.docker.compose.project=star-ecom-erp-api-dev
docker network inspect star-ecom-erp-api-dev_default \
  --format '{{range .IPAM.Config}}{{.Subnet}} {{.Gateway}}{{end}}'
```
首次部署尚无网络时，可先只启动该环境 Redis，让 Docker 自动分配网络，再返回检查；不指定固定 subnet，也不需要启动尚未就绪的 app。操作流程：

1. 按 §4 在可信本机准备 `dev` 的受保护 env，将**经审查的待合并版本** `docker-compose.yml` 一并准备好，不混用旧编排。
2. 在宿主机执行 `umask 077; mktemp -d /home/edward/redis-bootstrap.XXXXXX`，记录返回的目录。在 §4 的本机临时文件清理前执行以下传输，env 命名为 `.env`；不要覆盖 CI 的活动目录：
   ```bash
   REMOTE_BOOTSTRAP='<returned-absolute-directory>'
   scp "$WORKTREE/docker-compose.yml" "edward@xq-local.tail08f53.ts.net:$REMOTE_BOOTSTRAP/docker-compose.yml"
   scp "$APP_ENV_PATH" "edward@xq-local.tail08f53.ts.net:$REMOTE_BOOTSTRAP/.env"
   ```
3. 在宿主机同一个 Bash 会话执行以下命令（替换目录），仅启动 Redis：
   ```bash
   BOOTSTRAP_DIR='<returned-absolute-directory>'
   chmod 600 "$BOOTSTRAP_DIR/.env"
   export APP_ENV_FILE="$BOOTSTRAP_DIR/.env"
   docker compose --env-file "$APP_ENV_FILE" -f "$BOOTSTRAP_DIR/docker-compose.yml" \
     -p star-ecom-erp-api-dev config --quiet > /dev/null 2>&1 &&
   docker compose --env-file "$APP_ENV_FILE" -f "$BOOTSTRAP_DIR/docker-compose.yml" \
     -p star-ecom-erp-api-dev pull redis &&
   docker compose --env-file "$APP_ENV_FILE" -f "$BOOTSTRAP_DIR/docker-compose.yml" \
     -p star-ecom-erp-api-dev up -d --pull never --wait --wait-timeout 300 redis
   ```
4. 成功后重新 inspect 网络，保留此 project 的网络和 Redis 卷供首次 CI 使用，不执行 `down`。删除暂存 `.env` / compose 并 `rmdir` 暂存目录、`unset APP_ENV_FILE`；Redis 容器中的 env 仍是 Docker 特权可读。后续 `test/main` 按对应 project 单独操作。

用实际 user-defined subnet 的网络地址/掩码限定 MySQL 账号 Host；多环境或多条合法来源分别授权，不用 `%` 通配所有主机。下面 **`172.20.0.0/255.255.0.0` 仅演示掩码写法，不能照抄**。先备份并检查已有账号，使用 `sudo env MYSQL_HISTFILE=/dev/null mysql` 的交互提示符执行；密码只在该无历史交互会话或本机权限 600 的编辑文件中填写，不用 `mysql -p明文`、shell heredoc 或 `gh --body` 传真值：
```sql
CREATE DATABASE `star-ecom-dev` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'star_dev'@'172.20.0.0/255.255.0.0' IDENTIFIED BY '<dev-database-password>';
GRANT SELECT, INSERT, UPDATE, DELETE ON `star-ecom-dev`.* TO 'star_dev'@'172.20.0.0/255.255.0.0';
SHOW GRANTS FOR 'star_dev'@'172.20.0.0/255.255.0.0';
```
账号 Host 的每处都替换为实际值；这是基础运行权限，额外权限由后端负责人按模块确认，迁移使用单独维护账号。不要远程 root 登录、`GRANT ... ON *.*` 或给应用全局管理权限。若已有账号/库，检查后再作增量变更，不能删库重建。网络重新分配后须重新核对授权和防火墙；不要临时放宽至 `%` 排障。

从 tailnet 与内网直连的管理 / 维护访问另建独立账号，Host 显式覆盖两类来源，口令不复用应用账号：
```sql
CREATE USER 'star_admin'@'100.64.0.0/255.192.0.0' IDENTIFIED BY '<admin-database-password>';
CREATE USER 'star_admin'@'192.168.1.0/255.255.255.0' IDENTIFIED BY '<admin-database-password>';
GRANT ALL PRIVILEGES ON `<env-database>`.* TO 'star_admin'@'100.64.0.0/255.192.0.0';
GRANT ALL PRIVILEGES ON `<env-database>`.* TO 'star_admin'@'192.168.1.0/255.255.255.0';
```
`100.64.0.0/255.192.0.0` 为 Tailscale CGNAT 段（`100.64.0.0/10`）的掩码写法，按实际使用范围收紧；管理账号口令同样按密钥规范管理。

完成 ufw 放行并生效后，在实际网络内验证连接与 `CURRENT_USER()`，口令由客户端提示交互输入。下面只启动临时客户端，MySQL 服务仍由宿主机 APT 安装，不使用特权模式：
```bash
docker run --rm -it --network star-ecom-erp-api-dev_default \
  --add-host host.docker.internal:host-gateway mysql:8.4 \
  mysql -h host.docker.internal -u star_dev -p -D star-ecom-dev \
  -e 'SELECT CURRENT_USER(), DATABASE();'
```

**安装成功、建空库均不等于应用可用。仓库没有可直接一键导入的权威完整初始化脚本：**
- `sql/mysql/ruoyi-vue-pro.sql` 缺少 XQ 与 Quartz，不能独立初始化当前应用。
- `sql/mysql/quartz.sql` 含调度器状态及破坏性 DROP，不能直接当作干净建表迁移。
- `sync-local-to-prod` 类 SQL 含用户/密钥数据，不能当作种子导入；禁止通配导入 `sql/**/*.sql` 或未经审查的 dump。

后端负责人须提供覆盖**当前全部启用模块（含 XQ）及 Quartz** 的经验证 schema + 脱敏必要种子，或批准从既有数据库迁移；确认版本、权限、备份与恢复方案后才导入。prod 的 Quartz `initialize-schema: NEVER`，不会自动补表，也不能改成自动初始化来绕过此步骤。复制含加密行的数据时，`MYBATIS_ENCRYPTOR_PASSWORD` 必须与原数据匹配（密钥规范 §7.2）；不能为了满足长度校验直接换新 key。验收还需确认可登录的受控初始账号、必要配置以及应用查询/调度能工作；缺少负责人确认的初始化材料时，**合并前准备仍未完成**。

### 3.5 合并前验收

- `dev`：管理员完成 MySQL 安装、四地址绑定与 ufw 放行（§3.3）、独立数据库与账号、经确认的 schema/种子；实际容器网络可访问数据库（ufw 规则与账号 Host 双重核对），tailnet / 内网侧各实测一次连接，Redis 已可按编排健康启动。
- GitHub：仓库变量和 SSH/OAuth secrets 就绪，`dev` 分支限制与整份 `APP_ENV` 已核对；`test/main` 在各自首次部署前重复数据库和密钥准备，`main` 审批不可省略。
- 主机还有 Bash、`flock`、`python3`、`curl`，部署账号可使用 Docker / Compose **>= 2.20**、写入 `DEPLOY_PATH`、拉取 GHCR；核对 §1 的路由与前端映射。CI 创建环境部署目录，不代装 MySQL、不建库或补 schema。
- 由负责人检查 PR #8 的检查结果后决定合并，不自动执行 merge。合并引发的首次 dev 部署按 §2 验收 app、Redis 镜像与健康、数据库连接，再验证前端登录/API；预检不能代替运行验收。

## 4. `APP_ENV` 写法与校验

以 `.env.example` 为模板，只填需覆盖的值；**`KEY=` 是明确空字符串，不会回退到 Spring 默认值**，不需覆盖的项应注释或删除。
模板已注释 `XQ_RPA_CALLBACK_BASE_URL`，以保留从 `XQ_PUBLIC_HOST` 派生的默认 URL；`XQ_ERP_BASE_URL` 已无代码消费者，连同 prod 配置一起移除。第三段不用的 AI 键也已注释。

以 `dev` 为例，至少核对以下连接与密钥项；尖括号都是占位符，不能原样提交为 secret。`test/main` 分别替换库、应用账号、口令；字段加密 key 按数据来源核对，不机械生成：
```dotenv
MYSQL_HOST=host.docker.internal
MYSQL_PORT=3306
MYSQL_DATABASE=star-ecom-dev
MASTER_DATASOURCE_USERNAME=star_dev
MASTER_DATASOURCE_PASSWORD='<dev-database-password>'
REDIS_HOST=redis
REDIS_PORT=6379
REDIS_DATABASE=0
REDIS_PASSWORD='<dev-redis-password>'
MYBATIS_ENCRYPTOR_PASSWORD='<matching-encryption-key>'
```
模板用户名留空，必须填写受限应用账号；不能依赖 YAML 的 root 默认值。Redis 地址固定为服务名 `redis`，口令必填且每环境不同。`REDIS_PORT` 由应用、Redis 监听和健康检查共同使用，默认 6379，可设 1–65535，不是宿主机映射端口；`REDIS_DATABASE` 默认 0，范围 0–15，各环境依靠独立实例和卷隔离而非仅靠库号。

先读取 §3.1 的现有 Environment 配置，从授权保管者取得完整现有应用配置，再用受保护编辑器补齐；上传是**整份替换**，不要把已有功能项遗漏。以下在可信本机准备临时文件并上传，调整 `WORKTREE` 为本机已审查的工作区。不要开启 `set -x`、录屏或编辑器云同步：
```bash
(
  umask 077
  REPO=Ellean/ruoyi-vue-pro
  ENV=dev                     # test/main 在各自首次部署前分别执行，不复用 dev 凭据
  WORKTREE='/absolute/path/to/ruoyi-vue-pro'
  SECRET_DIR=$(mktemp -d "${TMPDIR:-/tmp}/app-env.XXXXXX") || exit 1
  APP_ENV_PATH="$SECRET_DIR/.env"
  trap 'rm -f "$APP_ENV_PATH"; rmdir "$SECRET_DIR"' EXIT
  cp "$WORKTREE/.env.example" "$APP_ENV_PATH" || exit 1
  chmod 600 "$APP_ENV_PATH"
  "${EDITOR:-vi}" "$APP_ENV_PATH" || exit 1
  # 如需 §3.4 的 Redis 预启动，在此用 scp 传入宿主机的 700 临时目录；不打印文件
  gh secret set APP_ENV --repo "$REPO" --env "$ENV" < "$APP_ENV_PATH" || exit 1
  gh secret list --repo "$REPO" --env "$ENV"
)
```
应使用 `gh secret set APP_ENV --env <环境> < <受保护文件>`，**不要用 `gh secret set --env-file`**：后者会拆成多个 secret，而工作流只读取单个 `APP_ENV`。副本用完删除，编辑器备份/交换文件同样按密钥管理；普通删除不保证底层介质安全擦除。
本地长期运行需要 `.env` 时可用同样权限在仓库根准备，已有文件不得覆盖。`.env` / `.env.*` 被 gitignore，只有 `.env.example` 例外。

CI 的实际规则：
- 空行、注释可保留；其余必须是单行 `KEY=VALUE`。只允许模板中的键（含注释项）及 `JAVA_OPTS`，拒绝重复键、未知键和编排键。
- 不得写入 `COMPOSE_PROJECT_NAME`、`IMAGE_TAG`、`HOST_PORT`、`CONTAINER_NAME`、`HOST_BIND_IP`、`APP_ENV_FILE` 等编排键。
- 值含 `$` 必须用单引号包裹；密钥建议单引号引用，避免插值或空格后的 `#` 被当成注释。不要 `source` 此文件。
- 使用 `docker compose config --format json` 实际解析，警告或错误均失败；从解析后的运行环境校验，而非仅检查文本。
- `MASTER_DATASOURCE_USERNAME`、`MASTER_DATASOURCE_PASSWORD`、`REDIS_PASSWORD`、`MYBATIS_ENCRYPTOR_PASSWORD` 必须非空；`REDIS_HOST` 必须填写为 `redis`；`MYSQL_HOST` 或完整 `MASTER_DATASOURCE_URL` 至少提供一个。
- `MYBATIS_ENCRYPTOR_PASSWORD` 必须为 **16/24/32 个 UTF-8 字节**；`SERVER_PORT`、`REDIS_PORT` 为 1–65535，`REDIS_DATABASE` 为 0–15。
- 长度合规不代表密钥匹配存量数据，需由操作者核实；不能为过校验擅自轮换（迁移见密钥规范 §7.2）。
- 配置校验错误不回显原文、值或解析器输出，仅给通用说明、行号或已知键名；成功只报告已验证，不输出配置。

## 5. 本地运行

在仓库根目录准备好 §4 的 `.env`，并确认宿主机 MySQL、数据库和来源授权就绪后：
```bash
docker compose pull app redis
docker compose up -d --pull never --wait --wait-timeout 300 app redis
docker compose logs -f app redis
```
本地默认访问 `127.0.0.1:8022`，Redis 不发布主机端口。Compose **没有 `build` 定义**；本地构建并运行必须禁止自动拉取覆盖本地镜像：
```bash
docker compose pull redis
docker build -t ghcr.io/ellean/ruoyi-vue-pro:dev .
IMAGE_TAG=dev docker compose up -d --pull never --wait --wait-timeout 300 app redis
```
这里只是本地运行，不会替代 §3 的服务器或 GitHub 配置。日常启动/更新保留 Redis 卷，不使用 `down -v`。

部署回归测试运行 `python3 script/test_deploy.py`，需要本机 Docker / Compose、Python 3、Ruby（YAML）；缺少 Redis 测试镜像时自动拉取。测试仅使用合成凭据和临时 project，验证鉴权、环境隔离、跨容器连接、端口覆盖与重建后 AOF 数据保留，结束只删除自身临时资源。CI 的 Test 腿也执行此测试，不连接真实 MySQL 或部署主机。

## 6. 手动回滚

`dev` 集成、`main` 发布；`:latest` 只跟随 `main`，不代表 dev 最新进度。
部署按**完整 SHA tag** 定位构建，但 tag 本身仍可覆盖，不是不可变或可复现的安全保证；不可覆盖策略或 digest 固定属于后续工作。
下载量取决于镜像层和本机缓存，不保证每次固定下载量。

1. **先暂停自动部署触发或等待在途部署完成，并确保回滚期间无新部署竞争**；不要直接取消正在变更容器的任务。
2. 经 tailnet SSH 登录，在同一个 Bash 会话进入目标环境目录并取得 CI 使用的同一把锁：
   ```bash
   cd /home/edward/star-ecom-erp-api/dev  # 按 DEPLOY_PATH 和目标分支调整
   exec 9>.deploy.lock
   flock -w 600 9 || exit 1
   export APP_ENV_FILE="$PWD/.env"
   ```
3. 确认活动 `.env` 和 `docker-compose.yml` 存在；使用失败后保留的配置，或在锁内仅将 `.env` 的 `IMAGE_TAG` 改为已知历史完整 SHA。不要改加密密钥。先核对运行中的 app / Redis 镜像、口令配置与持久化数据，旧 env 不保证仍匹配当前容器。
4. 确认旧应用兼容当前数据库 schema、Redis 版本与数据格式。`redis:7.4-alpine` 也是可变 tag，重新 pull 不保证拿到上次的 Redis；需要精确回退 Redis 时须先核对已记录的镜像 ID/digest 和 AOF 兼容性，并取得可恢复的数据备份。不得将不兼容旧版本直接挂到现有卷，也不能靠 `down -v`「修复」。
5. 保持锁，依次执行（适用于含 Redis 的现行编排；配置校验失败即停止，不输出含密钥的解析结果）：
   ```bash
   docker compose config --quiet > /dev/null 2>&1 &&
     docker compose pull app redis &&
     docker compose up -d --pull never --wait --wait-timeout 300 app redis
   ```
   回滚可能同时重建两个服务、重新应用旧 Redis 口令；不能只恢复 app 却忽略 Redis。更早的外部 Redis 编排不适用这组命令，须单独制定迁移/恢复方案。
6. 按 §2 分别核对 app、Redis 镜像 ID 和 `healthy`，再检查 SSH 内 HTTP 200/JSON `UP` 后才退出该会话释放锁、恢复自动部署。数据库/Redis 数据不随镜像回滚；首次失败没有旧配置时不能照此回滚，下一次成功 CI 会更新活动配置。

## 7. 排错与前端衔接

| 失败位置 / 现象 | 检查 |
| --- | --- |
| `Resolve deploy target` | 三项部署变量是否缺失或格式不合法 |
| `Render runtime .env` | §4 的格式、允许键、必填项、字节长度及端口；不要回显密钥 |
| `Deploy and verify over SSH` | SSH/OAuth、Docker 权限、网桥 IPv4、主机依赖、锁等待、app/Redis 拉取及健康检查 |
| 首次失败 / 容器不健康 | SSH 后运行 `docker logs --tail 200 star-ecom-erp-api-dev`（main/test 按 §1 换名）；用 `docker ps -a --filter label=com.docker.compose.project=star-ecom-erp-api-dev --filter label=com.docker.compose.service=redis` 找到 Redis 再看其日志，不依赖尚不存在的活动 Compose 文件 |
| MySQL 拒绝连接 / 缺表 | 核对监听、实际来源网段、受限账号授权和防火墙；缺 XQ/Quartz 表按 §3.4 找负责人确认初始化材料，不导入任意 SQL |
| 应用连 MySQL 超时（`Communications link failure`） | ufw 未放行应用网段的入站（§3.3 ufw 小节），或账号 Host 掩码与实际来源网段不符；从容器内用 `mysql` 客户端实测区分 |
| `mysql.service` 启动失败 | `bind-address` 含本机不存在的地址（网卡未就绪 / DHCP 漂移 / tailscaled 未启动）或 `Restart=on-failure` 重试循环；核对 `sudo journalctl -u mysql` 与 §3.3 的地址列表 |
| Redis 认证 / 连接失败 | `REDIS_HOST=redis`、两服务共用端口和口令；候选部署失败后实际 Redis 可能已切换口令，不能只看旧 `.env` |
| 后端健康但前端 502 | 前端对应分支 `BACKEND_UPSTREAM` 应为 `host.docker.internal:802x`，同时核对 §1 网络前提 |

日志也可能含业务数据，分享前脱敏；不要输出完整 `docker inspect` 或 `docker compose config` 的环境变量来排错。
前端反代切换在前端仓库完成；切换后验证登录、API、文档页和 websocket。本仓库不声称前端当前已切换。
